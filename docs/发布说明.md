# 发布说明

ADisplay —— 把 Windows、macOS、Android TV 变成 AirPlay / DLNA 接收端。仅个人自用。

## 安装

| 平台 | 文件 | 说明 |
| --- | --- | --- |
| Windows x64 / ARM64 | `adisplay-windows-x64.zip`、`adisplay-windows-arm64.zip` | 解压后运行 `ADisplay.exe`。首次运行要放行 SmartScreen 与**防火墙**（必须勾「专用网络」，否则手机搜不到设备）。 |
| macOS（Apple Silicon + Intel） | `adisplay-macos-universal.dmg` | 打开 dmg 拖进「应用程序」。首次启动需在「隐私与安全性」放行，并**允许「本地网络」权限**。 |
| Android TV / 电视盒子 | `adisplay-android-tv.apk` | U 盘或 `adb install` 侧载。包里含 arm64-v8a 与 armeabi-v7a 两个 ABI。 |

详细步骤（系统会拦哪几下、搜不到设备时该查什么）见
[安装说明](https://github.com/cat-clever/ADisplay/blob/main/docs/安装说明.md)。

## 这一版（1.0.25）

- **Android TV：主页面重新整理**。默认突出开启接收、查看日志和修改名称，画质、语言、广播网卡与热点等低频选项收进「更多设置」，遥控器导航更短。
- **Android TV：播放器控制栏整合**。播放/暂停、快退 10 秒、快进 10 秒、进度条、日志和结束投屏统一放进播放器底部控制栏，不再额外显示右侧按钮；镜像页继续保留悬浮控制。
- **Android TV：修复横幅焦点与遥控器导航**。横幅出现后自动聚焦，并补充两个按钮之间的左右导航。

## 这一版（1.0.20）

- **Android TV：最低版本降到 Android 7.0（API 24）**。原来要求 Android 8.0
  （API 26）；在 Android 7 的电视盒子上侧载时，安装器只会报「解析软件包出现问题」，
  从提示上完全看不出是版本问题。核心库的 `.so` 本来就按 android-24 交叉编译
  （`CMakePresets.json`），代码里 API 26 才有的东西（通知渠道、
  `startForegroundService`）也都有 `Build.VERSION` 判断，所以只是把清单里的
  门槛放开，不需要改核心。
- 这一版同时包含 1.0.18 的焦点修复与 1.0.19 的 leanback 调整。

## 这一版（1.0.19）

- **Android TV：`android.software.leanback` 改为非必需**。原来声明成
  `required="true"`，一些手机和不上报 leanback 的电视盒子在侧载时会按「与设备
  不兼容」拦掉安装（表现为「解析失败」）。这个标志只影响应用商店的过滤，而本项目
  不上架商店；启动器靠的是 `LEANBACK_LAUNCHER`，与它无关 —— 改完之后电视启动器
  仍然能列出本应用。

## 这一版（1.0.18）

- **Android TV：修「结束投屏后遥控器够不到横幅」**。原来只有设备被识别成 Android TV
  （上报 `LEANBACK` / `TELEVISION`）时才自动抢焦点；电视盒子、手机接电视这类设备
  常常不上报，被误判成触屏后**没有任何元素持有焦点** —— 方向键按下去毫无反应，
  横幅上的「继续观看 / 断开投屏」永远够不着，只能去关服务。现在进入待机页、以及
  「继续观看」横幅出现时，都会主动把焦点放到第一个按钮上。
- **Android TV：焦点更明显**。聚焦的按钮放大 8%、底色提亮、白边框 —— 三米外也能
  一眼看出遥控器停在哪。

## 这一版（1.0.17）

- **Windows：修「有声音没画面」（另一条路径）**。上一版修的是镜像残留；这一版修的是
  中转判定：手机上的投屏 App 把分片名里的 `.ts` 去掉了，核心只看后缀会把播放列表
  判成「未知」而直接放行，Media Foundation 拿到 HEVC-in-TS 后只出声音、不出画面。
  现在扩展名认不出时会**拉第一片按内容再判一次**（TS 的 `0x47` 同步字节 / fMP4 的
  `ftyp` 等 box），是 TS 就照常换封装成 fMP4 再交给播放器。
- **Windows：`InvalidCastException` 首次出现时记录完整堆栈**，后续同样的失败不再
  重复记录。这行日志用来确认 `PlaybackSession` 投影失败的确切位置。

## 这一版（1.0.16）

- **Windows：修一个会导致「有声音没画面」的状态残留**。AirPlay 镜像的自解码那条路
  画上第一帧后会把 `MediaPlayerElement` 收起来、改由位图显示；之后再投 DLNA 时
  没有把它换回来 —— 音频由 `MediaPlayer` 直接出，视频却要靠
  `MediaPlayerElement` 的渲染面，于是只剩声音。现在每次 DLNA 起播前都会恢复
  播放器控件。
- **Windows：状态日志不再抛 `InvalidCastException`**。播放状态改成从应用自己持有
  的 `MediaPlayer` 读，不再依赖事件参数里的投影对象（部分机器上读它会抛）。
- **核心：中转把「直连还是换封装」的判断写进日志**
  （`本地中转：播放列表判为 fMP4，直连远端地址`）。以后遇到「有声音没画面」，
  一眼就能看出视频编码是发送端决定的还是我们换封装决定的。

## 这一版（1.0.15）

- **Windows：修「投屏刚打开就闪退」**（事件日志里的 `0xC000027B`，出错模块
  `CoreMessagingXP.dll`）。播放状态回调原先把 WinRT 的 `MediaPlaybackSession`
  留到界面线程再读；媒体失败 / 会话关闭之后那个对象已经失效，读属性会抛
  `RO_E_CLOSED`，而异常发生在 WinUI 的 DispatcherQueue 回调里，会被转成
  stowed exception 直接 fail-fast。现在状态与错误详情都在事件线程上当场读出，
  界面线程只拿到字符串。
- **界面侧的回调统一加兜底**：来自核心的投屏消息、播放器事件、定时器回调和
  日志派发，任何一步出错都只记一行日志，不再让整个进程退出。
- 每秒一次的状态回报与缓冲监测失败只记第一次，避免把日志刷满。

## 这一版（1.0.14）

- **Windows：播放路径上的异常不再带走进程**。与 Android 端 1.0.13 的做法对齐：
  - 起播（设置媒体源 + `Play`）失败时记一行日志并退回待机页，会话本身还留着，
    「继续观看 / 断开投屏」照常可用；
  - 手机发来的播放命令（播放 / 暂停 / 拖动 / 音量 / 静音）执行失败只记日志、
    作废这一条，不影响后续操作；
  - 拖动位置先夹到合法范围（负数按 0，已知时长时不超过时长），避免 WinRT 对
    非法 `Position` 抛异常。
- 这一版没有功能变化，只是把「播放出错 = 闪退」改成「播放出错 = 有日志、有退路」。
  配合 1.0.13 加的 `ADisplay-runtime.log` / `ADisplay-startup.log` /
  `ADisplay-crash.dmp`，下次再出问题能直接拿到现场。

## 这一版（1.0.13）

- **Android TV：修「投 .m3u8 就闪退」**。手机推来的 HLS 地址（例如经中转服务给出的
  `resource.m3u8`）会在 `setMediaItem` 处直接崩掉：ExoPlayer 按 URL 后缀推断出 HLS，
  反射加载 `HlsMediaSource$Factory`，而 APK 里只打了 `media3-exoplayer` 本体、没打
  `media3-exoplayer-hls`，于是 `ClassNotFoundException` 在界面线程上没人接，进程退出。
  这一版把 HLS 模块打进去了，`.m3u8` 正常播放。
- **起播失败不再带走整个进程**。同一个位置加了兜底：媒体源类型不支持、编码器缺失这类
  异常会记一行日志并退回待机页，不会再表现为「一投屏就黑屏重启」。
- **Windows：崩溃后能留下现场**。以前界面日志只在内存里，原生崩溃（castcore /
  Media Foundation 里的访问违例）更是连日志都不留，用户只能说「崩了」。现在：
  - 界面日志实时写到 exe 同目录的 `ADisplay-runtime.log`（不可写时退到
    `%LOCALAPPDATA%\ADisplay\runtime.log`），每行都立刻落盘；
  - 原生崩溃会记下异常码、出错地址与所在模块（如 `castcore.dll+0x…`），并写出
    `ADisplay-crash.dmp`；
  - 正常关窗会在运行日志末尾留一行「应用正常退出」，没有这一行就是被硬结束的。

## 这一版（1.0.12）

- **三端新增一行设置「广播网卡」**（文档 6.3 里那条「允许选择广播网卡」，此前是个死机制：
  ABI 里有字段但没有任何代码读它）。两个选项：
  - **自动**（默认）：只在实际的局域网网卡上做设备发现，与规格一致；
  - **也包含 VPN / 虚拟网卡**：VPN、ZeroTier、Tailscale、VMware / WSL 这些网卡也一起广播。
  - 一个例外两种模式都适用：**整机没有任何真实网卡时（例如只挂着一条 VPN），「自动」也会
    用虚拟网卡** —— 否则一个可用地址都没有，设备发现根本不工作。
- **切换后立即生效，不用重启应用**：只重启 SSDP 那一半，mDNS 是系统发布的、不受影响，
  所以正在进行的 AirPlay 镜像不会被打断（DLNA 的控制器列表会闪一下，已建立的投屏不受影响）。
  设置存在核心的配置文件里，下次启动照旧。
- **一句话说清它解决不了什么**：**tun 模式的 OpenVPN 不转发组播**，所以手机连 OpenVPN
  时仍然搜不到设备 —— 换任何接收端都一样。这一项真正有用的是 **ZeroTier 这类二层覆盖网**、
  OpenVPN 的 tap 模式，以及「整机只有 VPN」的情况。另外 **AirPlay 的发现不受它影响**
  （那是系统 mDNS 在发布）。

## 这一版（1.0.11）

- **三端图标补齐并统一**。以前只有 Android TV 有图标，而且是白描边、透明底 —— 那份图形
  在电视的深色启动器上没问题，放到 Windows 资源管理器或 macOS 访达里（浅色背景）基本看不见。
  现在三端是同一套图形：深色圆角底 `#101418`、白色屏幕轮廓、以及 TV 横幅一直在用的那点蓝
  `#4FC3F7`。
  - **Windows**：exe 的文件图标与窗口图标都设上了。两件事是分开的 —— exe 那份由 csproj
    嵌进去，而 WinUI 的窗口**不会**自己去用它，得在窗口起来时显式设一次（主窗与日志窗都要）。
  - **macOS**：`.app` 包里带上了 `.icns`，Dock 与访达里显示的就是它。
  - **Android TV**：启动器图标与横幅都按同一套比例重画（启动器补上了深色底）。
- **一致性不靠记性**：三端比例写成两份生成器里各一行 `PROPORTIONS`，CI 会把它们对表、
  并按比例反算 Android 矢量里实际用的数字 —— 改了一端忘了另外两端就会红。
  图标本身用 `tools/icons/make_icons.sh` 一条命令可复现地重做。

## 这一版（1.0.10）

- **macOS：修「结束投屏 → 继续观看之后一直黑屏」**。这是 Android 端 1.0.1 修过的同一个
  病灶，macOS 之前没跟上（当时的判断是「等发送端下一个关键帧」，而那份日志证明它等不来）。
  日志说得很清楚：新的渲染面一路 `丢弃 N 帧（最近一次原因：还没有解码参数（SPS/PPS））`，
  累计丢到 312 帧，而核心那边整场只有 **1 个关键帧** —— macOS 的渲染层
  （`AVSampleBufferDisplayLayer`）随视图被摘出窗口而销毁，重建后既没有 SPS/PPS（建不出
  解码格式）、也没有可解的关键帧，于是每帧都被丢掉，而且**永远**好不了。
  现在改成与 Android 同一个做法：**投屏页一直留在视图树里**，结束时只把它缩到看不见
  （`scaleEffect`）并让开交互，设置页用不透明底色盖在上面 —— 渲染层与解码状态都留着，
  继续观看是即时的。
- 同一份日志还确认：Windows 从没这个问题，Android 1.0.1 起也没有 —— 三端现在一致。
  代价是「不看的时候也在解码」，与 Android 那边一样。
- 顺带：「结束投屏」与「继续观看」各写一行日志，下次一眼就能看出渲染面有没有被摘掉。

## 当前进度

批次 0–6 已完成，三端可用：AirPlay 屏幕镜像（画面与伴音）、DLNA 投屏、中英双语（可随时切换、
不必重启）、Android 端开机自启与双 ABI。**尚未实现**的是连接确认与屏幕 PIN / 白名单。
