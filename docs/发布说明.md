# 发布说明

ADisplay —— 把 Windows、macOS、Android TV 变成 AirPlay / DLNA 接收端。仅个人自用。

## 安装

| 平台 | 文件 | 说明 |
| --- | --- | --- |
| Windows x64 / ARM64 | `adisplay-windows-x64.zip`、`adisplay-windows-arm64.zip` | 解压后运行 `ADisplay.exe`。首次运行要放行 SmartScreen 与**防火墙**（必须勾「专用网络」，否则手机搜不到设备）。 |
| macOS（Apple Silicon + Intel） | `adisplay-macos-universal.dmg` | 打开 dmg 拖进「应用程序」。首次启动需在「隐私与安全性」放行，并**允许「本地网络」权限**。 |
| Android TV / 电视盒子 | `adisplay-android-tv.apk` | U 盘或 `adb install` 侧载。包里含 arm64-v8a 与 armeabi-v7a 两个 ABI。 |

详细步骤（系统会拦哪几下、搜不到设备时该查什么）见
[安装说明](https://github.com/cat-clever/ADisplay/blob/main/docs/安装说明.md)。

## 这一版（1.0.9）

- **上一版那个补丁打歪了，这一版打正**。「丢几个包就静两三秒」的根因确实是 UxPlay 的
  音频缓冲区在等那个缺失的包，但 1.0.8 的超时**每个洞各计一次时**，而一次事件往往是
  连着丢好几个包 —— 7～9 个包 × 400 毫秒，正好又是三秒，白改（实测 2996 / 3204 / 3182 /
  3112 / 3458 / 3621 毫秒，和没打补丁时一样）。现在改成**一整串洞只等 200 毫秒**，
  然后一次跳过去。预计静音从三秒降到 0.2 秒上下。
- **同一份日志还纠正了两句错话**：那几秒里**画面一直在走**（视频计数每 5 秒稳定 +150 帧，
  满速 30 fps），停的只有伴音这一条流。所以「这段静音是发送端造成的」以及日志里那句
  「画面同时也停」都是我写错的，已经改掉，日志只陈述量到的事实。
- **新增一行诊断**：每次跳过缺失的包，记一行「ADisplay 伴音：跳过 N 个缺失的包（在洞上等了
  M 毫秒）」。这是唯一能分辨「重发没来」和「洞太大」的证据 —— 实测每个洞都等满了整段时间，
  说明我们请求重发的包**始终没有到**，那一截等待纯属白等，所以这一版把等待压到 200 毫秒。
- **导出日志之后画面变黑：加了完整的留痕，并修掉一个很可能的根因**。占位输出面以前写死
  `320x180`，而解码器是按 1920×1080 配的 —— 给它一块装不下一帧画面的面，
  真机上 `setOutputSurface` 就会抛异常，于是退回「拆掉解码器重建」，而重建必须等发送端
  插关键帧（iOS 整场只插 1 个）→ 画面就一直是黑的。现在占位面按解码器尺寸建，
  并且**换面的成功/失败、重建的原因与次数、换面后有没有重新出画面**都会写进日志。
  这一条我还没能在真机上证明，请你按下面那张日志来判断它到底好没好。

## 这一版（1.0.8）

- **修「丢几个包就静两三秒」**（这是追了几轮的那个断续声的根因）。UxPlay 的出队逻辑是：
  队首那个包没到时，**只要缓冲区还有空位就一直等重发** —— 等到缓冲被填满才肯往下走。
  缓冲 256 个包、AAC-ELD 每包 10.9 毫秒，于是**每次卡住约 2.8 秒**；实测的静音正是
  2.8–4.7 秒（这份日志里六次分别是 3111 / 2879 / 3506 / 4734 / 3180 / 765 毫秒）。
  改动：给缺失的包加一个 **400 毫秒**的超时，超时就往前跳、把那一小段丢掉 ——
  丢一小段远好过静几秒。这是本项目给 UxPlay 打的第三处补丁。

## 这一版（1.0.7）

- **修「点了导出日志之后画面就冻住」**：导出会打开系统的文件选择器，我们被切到后台 →
  SurfaceView 的 surface 被销毁 → 解码器跟着释放 → 回来得重建解码器，而重建必须等发送端
  下一个**关键帧**，iOS 插关键帧极稀（实测一份 1956 帧的日志里只有 1 个）→ 画面一冻就是很久。
  现在解码器**不随面销毁而释放**：把它的输出切到一个占位面（继续解码、输出丢掉），
  回来时再切回真面，第一个 P 帧就能画出来。顺带把「参数集不全」那条提示限流
  （以前每帧都打，一次会话刷了 521 行）。
  这一条同样修掉了「中途切到别的应用、回来画面冻住」。
- **日志诊断的结论**（来自你导出的那份日志）：伴音那几次静音是 **765 毫秒 ~ 4.7 秒**，
  与我们记的「上游停了 N 毫秒」完全对上，而且我们的伴音管道**全程没有重建过**
  （`已开始播放` 只出现 1 次）—— 也就是那几秒音频帧确实没到，不是接收端把它拆了。
  同一时刻协议层在刷大量重传（最猛 2 秒 48931 条），说明那几秒在大量丢包/重传。

## 当前进度

批次 0–6 已完成，三端可用：AirPlay 屏幕镜像（画面与伴音）、DLNA 投屏、中英双语（可随时切换、
不必重启）、Android 端开机自启与双 ABI。**尚未实现**的是连接确认与屏幕 PIN / 白名单。
