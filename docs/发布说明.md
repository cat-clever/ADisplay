## 安装

各平台的安装步骤、系统拦截怎么放行、搜不到设备时该查什么，
见仓库里的 [安装说明](https://github.com/cat-clever/ADisplay/blob/main/docs/安装说明.md)。

| 平台 | 文件 | 说明 |
| --- | --- | --- |
| Windows x64 | `adisplay-windows-x64.zip` | 解压后运行 `ADisplay.exe`。首次运行放行 SmartScreen 与**防火墙**（必须勾「专用网络」，否则手机搜不到设备）。 |
| Windows ARM64 | `adisplay-windows-arm64.zip` | 同上。适用于骁龙 X 系列等 ARM 笔记本，原生运行。 |
| macOS（Apple Silicon + Intel） | `adisplay-macos-universal.dmg` | 打开 dmg 拖进「应用程序」。首次启动需在「隐私与安全性」放行，并**允许「本地网络」权限**（否则广播会被系统静默拦掉）。 |
| Android TV / 电视盒子 | `adisplay-android-tv.apk` | U 盘或 `adb install` 侧载。 |

### 这一版的修复

- **iPhone 的「屏幕镜像」有画面了。** 上一版修好了「连上却不发流」，帧已经持续到达，
  但没人把它画出来。这一版补上渲染：macOS 用 AVSampleBufferDisplayLayer —— 它直接
  吃压缩的 H.264/H.265 并自己硬解，延迟最低，也省掉在核心里养一套解码加渲染。
  这与「解码渲染交给平台实现」这条一贯分工一致（DLNA 交给 AVPlayer，镜像交给这个层）。

- **渲染的格式一开始弄反了：核心给的是 Annex B，显示层要的是 AVCC。** 前者是
  `00 00 00 01` 起始码分隔，后者是 4 字节长度前缀。这类错最阴的地方是「看着像在跑」——
  帧照样计数、切出来的东西也能入队，只是解码器一个 NALU 都认不出来，屏幕全黑，
  很容易被当成「渲染没接上」而去查别处。现在先按起始码切开、重新按长度前缀拼一遍。

  （定位靠的是真机日志里那两行参数集：`SPS+PPS header: 01 64 00 1f ff e1` 是 avcC
  的写法，而交给渲染端的却是起始码形式。修完用日志里那两个真实的参数集字节做了本地
  核对：切分、挑参数集、转换长度前缀全部通过。）

- **iPhone 的「屏幕镜像」之前能连上却不投屏，根因是能力位（features）的两个 32 位
  半字写反了。** 现象很有迷惑性：手机能搜到、能连上，`pair-setup` / `pair-verify` /
  `fp-setup` 全部成功，`SETUP` 与 `RECORD` 都返回 200，然后 iOS 就不发流了 ——
  协议层日志里一行错误都没有。

  协议层把能力位拆成两个 32 位半字，约定是第一个在**低**位、第二个在高位，
  `/info` 应答里那个 64 位整数是 `(第二个 << 32) | 第一个`。我们按相反的方向拼了，
  于是 mDNS 通告里的字符串 `0x5A7FFEE6,0x0` 是对的，`/info` 里的整数却是
  `0x5A7FFEE6_00000000` —— **两边声明的能力不一致，iOS 连到一半就不再往下走。**

  定位方式是：在本机把协议层单独编成一个最小的诊断程序（用它自己的 mDNS 注册与
  默认配置），同一台 iPhone 一次就投出了画面、视频帧持续到达 —— 由此排除「上游与
  iOS 版本不兼容」这个方向，再逐字节对比两次的 `/info` 应答，差异全在那一个整数上。

- **把 AirPlay 协议层的日志真正接到了日志窗口里。** 上一个版本只把协议层自己的
  日志级别调到了 DEBUG，但那一步不够 —— 它写出来的 DEBUG 日志走到我们的日志系统
  时，是按「Debug」转发的，而本项目日志默认级别是 Info，于是全被丢掉了。表现是
  手机能连上（我们自己那句「iPhone 请求连接」是 Info，出得来），随后协议层一片
  空白，然后连接失败，完全无从下手。

  现在协议层的 NOTICE / INFO / DEBUG 一律按 Info 转发。它把请求行、请求头、
  plist 正文、`fairplay_decrypt` 的返回值、走到哪条分支都记在这一层上，
  而它自己的 INFO 只有错误 —— 偏偏 AirPlay 失败最常见的样子就是「接收端这边
  一句错误都没有」。逐帧的数据仍然按 Debug 转发，那个量级不适合常开。

- **iPhone 的「屏幕镜像」之前能搜到、却永远连不上。** 原因在 mDNS：我们把本机
  IP（如 `192.168.137.167`）填进了 DNS-SD 的**主机名**字段，而那个字段要的是域名。
  填 IP 不会报错，但注册出来的 SRV/A 记录指向一个解析不出地址的名字 —— 手机通过
  组播能发现这台设备，真要连的时候却找不到地址。DLNA 之所以一直没事，是因为
  SSDP 直接给 IP，不经过名字解析。现在改成不指定主机名，交给系统公布本机主机名
  并为所有网卡发地址记录 —— 这台机器同时挂在两个网段上（手机热点与另一个
  局域网），钉死一个地址只会让另一边的设备够不着。

- **拖动进度条拖远了会卡住。** 中转的换封装是「一条道走到底」的（fMP4 的时间戳
  必须单调），所以生产一直是严格按播放列表顺序做的：请求第 n 份分片就得先把前面
  每一份都下载、换封装一遍。正常播放时没问题，拖动时不是 —— 跳到第 300 份就要
  先做 300 份，几百次网络往返加几百次换封装，播放器那边就是卡住不动，跳得越远
  卡得越久。现在跨度小（三份以内）仍然顺序补，跨度大则直接从目标那一份重开，
  并把时间轴起点抬到那一份的起始时刻（由 `EXTINF` 的累加值得来，播放器自己也是
  这么算的），新旧分片的时间戳接得住。

- **AirPlay 协议层的日志提到了 DEBUG。** 它把「收到哪个请求、走了哪条分支」记在
  DEBUG 上，而之前是 INFO —— 于是「能搜到连不上」这种问题在日志里一个字都没有，
  无从查起。

下面几条是 v0.5.9 发的，如果你是从更早的版本升上来，一并列出：

- **H.265/MPEG-TS 片源的本地换封装通了 —— 之前它每次分片都失败。** 卡了两轮，
  原因是我查错了地方。日志里那句 `写 fMP4 分片失败：Operation not permitted`
  看着像寻址（seek）的问题，实际是 movenc 拒绝 ADTS 封装的 AAC：TS 里每个音频帧
  带 0xFFF 同步头，而 MP4 要裸帧加一份独立的 AudioSpecificConfig。它返回的是
  裸的 `-1`，`av_strerror` 把这个值翻成「Operation not permitted」——
  文案与权限毫无关系。现在按上游提示挂上了 `aac_adtstoasc` 过滤器。

- **同一个换封装里的第二处顺序错误：写文件头时还没拿到音频配置。**
  `movenc` 写 `ftyp+moov` 时就要把 AudioSpecificConfig 放进 `esds`，而那份配置
  要等第一条音频包被解析出来才有。原来是「先写头、后收包」，于是 esds 残缺，
  播放器**拒绝打开整个文件**（日志里是 `Cannot Open`），而不是「只是没有声音」。
  现在改成写头之前先预读：读到的包先攒着（丢掉的话每个分片都会缺一小段声音），
  写完头再按原顺序处理。

- **两端界面统一成同一套结构。** 设置页（设备名称、接收服务、本机信息 + 日志入口）、
  投屏页（画面满幅，控制条紧贴画面下方）、以及独立的日志窗口。
  日志之所以移出去看：投屏时画面要占满窗口，而「一边看画面一边盯日志」恰好是
  排查投屏失败时最需要的样子。

- **投屏画面四周的留白去掉了。** 投屏时用户看的就是画面，任何一圈边距都是白扔的
  像素。Windows 那边顺带给播放器加了黑底 —— 画面比例与窗口不一致时留出来的
  是黑边而不是主题色的一块，看起来才像播放器。

- **全屏时收起控制条。** 那一条横在画面下面既挡画面又白占高度，在 macOS 上还
  因为背景浅显成一条白条。全屏里退出有 Esc，播放控制由播放器自带的那套负责。

- **日志可以跨行选中了。** 原来每行一块文本，便于虚拟化，但鼠标拖不出跨行的
  选区 —— 想复制中间一段只能一行一行来，而「把出错前后几行一起贴出去」恰好
  是看日志的人最常做的事。现在整份日志放在一块文本里。

### 这一版能做什么

- **手机投屏列表里能看到这台电脑**（mDNS 与 SSDP 广播）。
- **Android 视频 App 推过来的视频能播出画面与声音**，播放、暂停、拖动进度、调音量都由手机控制。
  解码、硬件加速与音画同步交给各平台自带的播放器（macOS 用 AVPlayer、Windows 用
  Media Foundation、电视端用 ExoPlayer）。
- **H.265 装在 MPEG-TS 里的片源也能放。** 这类片源（国内不少投屏 App 是直通源编码的）
  系统播放器常常不认，接收端会在本地把封装换成 fMP4 再交给播放器 —— 视频不重编码，
  所以不吃 CPU、画质不损失。
- **iPhone 能连上本机**，并且能通过 AirPlay 推送视频（手机给一条 HLS 地址，由接收端
  自己拉流播放）。这条路径和 Android 那边完全一样。

### 这一版还不能做什么

- **镜像的伴音还没有。** 屏幕镜像时 iPhone 只建了视频那一条流（`type 110`），
  音频那条要单独协商，还没做。
- **Windows 端的镜像画面还没有。** 渲染这一版只做了 macOS —— 那条路能本地验证，
  先把它验通再做 Windows（要走 Media Foundation）。
- **AirPlay 的连接确认弹窗还没有。** 手机请求连接时一律放行（与 Android 那边一致），
  也就是说任何设备都能连，没有二次确认。这是批次 6 的内容。
- **只有 64 位电视盒子能用。** 这一版只出了 arm64-v8a 的库，32 位老盒子装不上。
  电视端也还没编 AirPlay 协议层，Android 目前只能用 DLNA 那条路径。
- **连接确认弹窗、白名单、托盘常驻、开机自启、中英双语还没有**（批次 6）。
- **Linux 桌面端还没有界面。** 核心库在 Linux 上能编、测试也过，但没有 GTK 界面，
  所以 Linux 暂时只能当开发用途。
- 电视端的「停止接收投屏」会停掉整个接收服务，需要重新开启一次。
