## 批次 3：与原计划的路线差异（重要，不是欠账）

计划写的是「FFmpeg 解码 + 硬解优先自动降级 + Metal/D3D11 渲染 + Windows 用 libmpv 作
DLNA 播放内核」。实际落地的是：

- **DLNA 不在核心里解码**：核心只把媒体地址交给各平台**自带播放器**（Windows
  `MediaPlayerElement`、macOS `AVPlayer`、Android `ExoPlayer`）。
- **只有镜像在核心里解码**：AirPlay 镜像是实时流、要求「最新一帧立刻上屏」，交给系统
  播放器会先攒一段再开播（实测 12.6 秒，还会随重新缓冲累积）；所以那条路改成核心用
  FFmpeg 解成 BGRA、界面自己画。
- **libmpv 没有用上**。

理由：各平台自带播放器已经把硬解与音画同步做完了，DLNA 那条本来就只是「给一条 URL」，
再养一条自研解码渲染链是净亏；而镜像那条恰恰是系统播放器做不好的，才自己接管。

**中英双语的实现（三端同一套思路）**：不能重启应用，就用不了系统那套「启动时按
Configuration 取一次值」的资源系统（Android 的 values/、macOS 的 Localizable.strings、
WinUI 的 x:Uid + .resw 都是那个模型）。所以三端各自拿一份字符串表 + 一个语言状态：

- 电视端 `Strings.kt`（中英两个常驻实例）、macOS `Strings.swift`（protocol + 两个 struct）、
  Windows `Strings.cs`（一个类 + 两个常驻实例）。
- 语言状态挂在各端的界面模型上，改了立刻生效：Compose 靠重组、SwiftUI 靠 @Published、
  WinUI 靠一遍显式的 `ApplyLanguage()` 回填（XAML 的字是解析时定下的）。
- 存在各端自己的设置里：Android `SharedPreferences`、macOS `UserDefaults`、
  Windows `%LOCALAPPDATA%\ADisplay\language.txt`（绿色版没有包身份，
  `ApplicationData.Current` 会抛异常）。
- **日志一律中文，不跟着界面走**（用户 2026-10-11 的决定）；核心给的一些字符串
  （设备名校验的具体原因）同样是中文 —— 要翻得给 ABI 加错误码或做码表映射。
- 够不着的边界：桌面/启动器上的**应用名**（Android 的 strings.xml、macOS 主窗口标题、
  Windows 窗口标题）由系统在创建时读一次，跟不了应用内语言。

**中英双语的范围（提议，待确认）**：只翻**三端界面上的文字**，不翻日志。日志（核心与三端
打出来的那些行）保持中文 —— 它们是给人排查用的，而且核心里的日志是几百条中文长句，翻一遍
的收益远小于成本。各端的界面文字本来就都在各自那一层（`statusText`、`AdResult` / `ServiceState`
的 label、XAML / SwiftUI / Compose 里的字面量），核心的 C ABI 里没有给界面用的字符串，
所以这件事不需要动核心、也不需要动 ABI。

## 已知问题

1. **手机停止投屏后，待机页的横幅不消失**（三端，v0.5.83 起）。用户已知，暂不修。
2. **DLNA 的【断开投屏】是尽力而为**：DMR 协议上接收端是被动方，命令不了手机停止 —— 只能
   结束本地会话并推一条 `STOPPED` 事件，手机认不认取决于对方 App。AirPlay 那条则**真能**
   让 iPhone 停（走 UxPlay 公开的 `raop_remove_known_connections`，只拆连接、不停 httpd、
   不撤 mDNS，所以服务还在、手机随后还能再投）。
3. **恢复画面**：Windows 与 Android 都立刻有了 —— 它们的画面/解码器在会话期间一直留着
   （Android 是 v1.0.1 修的：结束投屏只是把画面缩成 1dp，解码器不释放）。**macOS 仍需等
   发送端下一个关键帧**（它的渲染面随页面销毁而重建），静止画面时 iOS 可能几十秒才插一个
   IDR；要照 Android 的办法修得有下一轮。
4. **Android 横幅的初始焦点不确定**：它与待机页原有「初始焦点给服务按钮」是两段独立的
   `LaunchedEffect`，谁最后执行没有保证。
5. 镜像延迟：v0.5.76（解码器单线程 + 日志窗口合并刷新）之后已确认修复。
6. **B 站换视频 / 重播 / 拖动进度条时，伴音短暂中断、画面卡一下再往前跳**（Android TV 镜像，
   2026-10-11 报）。
   **未定性**。这两种操作都**不会**改变镜像画面的尺寸，所以镜像流不会重新协商 ——
   按现有代码，我们这边没有会让伴音停下来的路径（只有「会话关闭」「用户点结束投屏」
   两条会收伴音）。因此更可能是**上游**：B 站自己换视频时的音频重缓冲，或 iOS 在应用
   重启音频会话时采集顿了一下。
   **一个量级上的判断**：拖动进度条那次的静音有 **2–3 秒**，而我们的伴音队列只有 8 帧
   （约 160 毫秒）—— 我们自己造不出那个量级的空档，那种时长只可能来自上游（App 拖动后
   重新缓冲，手机自己的声音先停了）。但要证明而不是"觉得"，所以：

   **第三个候选原因（我们这边，v1.0.2 起可以看日志定性）**：伴音队列只有 8 帧、满了丢最旧的，
   而 B 站换视频那一刻盒子的 CPU 会为新的视频内容忙一阵 —— 伴音线程被抢走时间片、队列溢出、
   丢帧，用户听到的就是断一下。v1.0.2 做了两件事：把伴音线程提到「紧急音频」优先级
   （音频断一下比掉一帧画面显眼，而画面那条本来就是「宁可按最新走、丢了也不补」）；
   丢帧时打日志。
   **怎么定性**：复现一次，看日志抽屉里那一刻有没有这三行中的哪一行 ——
   * `镜像伴音：队列满了，累计丢 N 帧` → 是我们这边丢帧（已提优先级，看还有没有）；
   * `镜像伴音：已开始播放（…）`（新的一行）→ 我们重建了播放端；
   * `镜像伴音：上游停了 N 毫秒没给帧` → **直接证据**：这段静音是发送端造成的
     （画面同时也停），我们无能为力。这是 v1.0.2 起才有的那把尺子 ——
     量的是相邻两帧**到达**的间隔；
   * 三行都没有、也没有 `解码线程出错` → 我们没丢帧、上游也没停，那问题在别处（继续查）。
   同样的诊断也加到了**画面**那条路（v1.0.2）：`镜像渲染：队列满了，累计丢 N 帧` ——
   画面「卡一下再突然加速」如果是我们丢帧造成的，就会出现这一行；不出现而画面照样卡，
   那就是上游压根没给帧（iOS 的镜像管线顿了一下再补一波），我们无能为力。
   另一个更快的办法：不投屏、只在手机上看同一个视频，上滑切换时如果手机自己也顿一下，
   那就是 B 站的行为。

7. **Windows 点主窗的 X 关不掉**（用户报过两次，v0.5.89 起带诊断）。两个可能的原因都
   真实发生过 —— 日志窗盖住主窗的 X（点在日志窗上了，见 `PlaceLogWindow`），或者收尾
   卡住（日志窗那步很快、看得见，后面几步卡住完全没有反馈）。v0.5.89 把收尾挪到后台并
   加了 3 秒上限（**保证点一定退**），每一步耗时写进 StartupLog —— 下次再出现时看那几行
   就能分开是哪种：写着「收尾超时」是卡住，写着毫秒级完成就是点在别的窗口上了。

## 已决定暂缓（以后可能做）

这些不是"忘了做"，是**有意先放着、以后可能捡起来**。每条都带上以后接手需要的东西。

### 连接确认 + 屏幕 PIN + 白名单/黑名单 ← 用户明确说"先不做，但记下来"

- **是什么**（文档 §2.1 第 5 条 / §2.3 / §3.1 / §7）：首次连接时在**接收端**上确认 ——
  显示设备名与类型、以及一个 **6 位 PIN**（供用户与手机上显示的对一下），用户选
  「**允许一次 / 始终允许 / 拒绝**」。PIN 是**看**的、不是输的（电视没键盘）。首次确认后
  以设备证书/令牌免确认。目的：**防止同网段陌生人投屏骚扰**。
- **现状**：`ad_engine_respond_connect_request`（`core/api/src/AdEngine.cpp`）仍是空壳，
  `AdConfig.require_confirmation` 也没接。
- **不做期间的现实**：**同一局域网内任何人只要知道地址就能直接投上来，没有任何确认环节。**
- **要做的话动哪**：
  - 核心：在**开会话之前**拦一道（生成/校验 PIN、白名单/黑名单、同时连接数限制、
    `require_confirmation` 开关），确认结果再决定放不放行。
  - 三端界面：各做一个确认框 —— 电视端用遥控器选中，桌面端鼠标点。
  - 文档 §6.2 里「会议室模式：仅允许 PIN」是同一批。
- **相关的现成接口**：`AdCallbacks.on_connect_request` / `ad_engine_respond_connect_request`
  这两个口子在 C ABI 里**已经定义好了**（只是核心没实现），所以不必改 ABI。

### 手机停止投屏后，待机页的横幅不消失 ← 用户明确说"先不修"

- **现象**（三端，v0.5.83 起）：手机那头停了投屏，接收端待机页上那条「还能回去」的横幅还挂着。
- **原因**：横幅的显示条件现在只看"本地是否被用户结束"，没跟着 `on_session_closed` 一起收。
- **改法**：会话关闭的回调里把横幅状态清掉即可 —— 是个明确的小改动。

### 待机页的连接说明加二维码 ← 用户 2026-10-11 说"先不做"

- **是什么**（文档 §2.3 电视端要求 / §3.3 发现与配对）：待机页那条连接说明旁边放一个二维码。
- **两个出处说的其实是两件事**：§3.3 是自研协议 `castpc` 的**备选配对方式**（码里放
  IP、端口、一次性令牌，用来绕开「路由器屏蔽组播」这类情况）；§2.3 只说「方便手机用户
  找到设备」。
- **为什么现在做没用**：`castpc` 客户端不存在，**没有任何 App 会去解析这个码** —— 手机
  相机扫出来只会显示一串文本。而 §2.3 那条对 AirPlay / DLNA 站不住：手机发现设备靠的是
  mDNS / SSDP 组播，扫码不会让这台电视出现在 iPhone 的「屏幕镜像」列表里。今天唯一沾边
  的用途是「DLNA 类 App 支持手填地址时，扫码把地址复制出来」，而这件事待机页上那行
  「本机地址」已经用文字做了。
- **要做的话怎么放**：与 `castpc` 一起做 —— 同一个位置改成「IP + 端口 + 一次性令牌」的
  配对载荷，而那套令牌机制与上面的「连接确认 + 屏幕 PIN」是同一批。真要在那之前先放点
  东西，就放**本机地址**（扫码可复制），不要先自己造一套令牌格式。
- **依赖**：需要一个二维码生成库（如 `com.google.zxing:core`，纯 Java，APK 里约 250KB）。
  不建议自己写编码 —— QR 的纠错码与掩码挑错一处就是「扫不出来」，而那种错只在真机上
  看得见。

## 决定不做 / 未做的方向

### Miracast 接收端：**不做**

结论有证据支撑（不是"感觉难"）：

- **它是「平台能力」，不是「应用能力」** —— 能收 Miracast 的设备无一例外是系统的拥有者：
  Android 盒子/电视用 AOSP 自带的 wifi-display sink（编在系统镜像里），品牌电视用自家固件，
  Windows 用系统组件「无线显示器」，廉价投屏器用芯片厂的专有 SDK。
- Windows：`Windows.Media.Miracast.MiracastReceiver` 要 **UWP 的 `CoreApplicationView`**，
  WinUI 3 桌面应用拿不到；且这一族属于「桌面应用不支持」的 API，社区实测「能创建、一投就
  unknown error」。
- macOS：没有任何对应用开放的路径（系统只做 AirPlay，wpa_supplicant 的 P2P 也不可用）。
- Android：sink 是 framework 层；唯一绕法是特权 helper（与「不要系统特权」冲突）。
- 跨平台库：最接近的 MiracleCast 绑死 Linux（systemd/sd-bus/wpa_supplicant/GStreamer），
  且它自己的接收端功能标注 "not implemented yet"。

**零成本替代**：在这台 Windows 上启用系统自带的「无线显示器」（设置 → 系统 → 投影到此电脑），
Android 手机就能投上去 —— 代价是画面进系统的接收窗口，用不上本程序的界面与控制。

### 电视端的 x86 / x86_64 ABI：**不做**

开发文档 M6 的「全 ABI」是 arm64-v8a、armeabi-v7a、x86_64、x86 四个。现在打的是前两个
（`app-tv/app/build.gradle.kts` 的 `abiFilters`），后两个**有意不打**：

- 它们只服务模拟器与极少数 x86 盒子，而电视盒子（Fire TV、Chromecast、主流国产盒子、
  各种老安卓盒子）清一色是 ARM。
- 每个 ABI 都要在 CI 里多编一份 `libcastcore.so`（含 OpenSSL、libplist、UxPlay 那一串），
  还要多一截 APK 体积 —— 换来的是一个几乎不存在的目标。

真要做，顺序和加 armeabi-v7a 时一样：先在 CI 里编出对应 ABI 的 `.so`，再往 `abiFilters`
里加一行。**反过来先改 `abiFilters` 是不行的** —— 列了却没有对应的 .so，Android 装的时候
不报错，装上跑起来才在 `System.loadLibrary` 处抛 `UnsatisfiedLinkError`，表现是「装上就闪退」。

### 自研协议 + 配套 Android 客户端（文档 §3.3，P1）：**未做**

`protocols/castpc/` 与 `android-client/` 目前都是**空目录**，也没有接进 CI。

它是「用自己的界面收 Android 手机整屏」的正路（接收端广播 `_castpc._tcp`，手机 App 用
NsdManager 发现），而且协议里带**关键帧请求** —— 那正好能解掉 AirPlay 镜像上「发送端不插
I 帧时只能干等」的问题。

### 「开热点」只做「跳系统设置页」，不做程序开 ← 用户 2026-10-11 定，同日实现

**先说结论，免得以后重新查一遍：真热点（带上网共享）第三方应用开不了，这是系统明确禁止的。**
AOSP 里 `ConnectivityManager.startTethering` 标着 `@SystemApi` + `@hide`，校验的权限是
`android.permission.TETHER_PRIVILEGED`，源码注释写着「must only let system apps (which check
this app) turn on tethering」；老的 `WifiManager.setWifiApEnabled` 更早就被隐藏、并在 API 30
前后删除。第三方要开真热点只剩 root / 改 ROM / 平台签名三条路 —— 都跟本项目「不要系统
特权」的前提冲突（同 Miracast 那节的结论）。所以公开 API 参考里也查不到 `TetheringManager`
这些类：`@SystemApi` 的东西不进公开文档。

**因此做法是：给一个入口跳到系统的热点设置页，用户自己按一下。**（v0.5.87 起）

- **入口在电视端**（待机页最下面「打开热点设置」），不在手机端 —— 用户 2026-10-11 指正的。
  方向是**电视开热点、手机连过来**：盒子插着电、位置固定、常年开着；反过来让手机开热点的话，
  得在电视上用遥控器敲 Wi-Fi 密码，而且手机还费电。
- **不要只跳一个 action。** `android.settings.TETHER_SETTINGS` 这类具体页面**不是每台设备
  都有**（电视端尤其明显：很多 Android TV 的设置里根本没有热点那一页），跳不到会抛
  `ActivityNotFoundException`（Kiwix 在手机端踩过：`kiwix-android` PR #4501）。所以代码里依次试
  `android.settings.TETHER_SETTINGS` → `android.settings.panel.ACTION_INTERNET_CONNECTIVITY`
  （Android 10 起的公开设置面板）→ `Settings.ACTION_WIRELESS_SETTINGS`，三个都跳不到就在界面上
  把话说清楚并记一条日志 —— 不能按了没反应。
- **iOS 那边同样没有 API**（那是手机端以后的事），连「直达个人热点页」都只能靠私有 scheme
  （`App-Prefs:root=INTERNET_TETHERING`，上架必被拒）。自用侧载可以试，但不保证各版本都灵。

**另一条能程序化开的是「本地热点」**（`WifiManager.startLocalOnlyHotspot`，公开 API，Android 8+，
13+ 要 `NEARBY_WIFI_DEVICES`）。它**不给客户端上网** —— 官方指南原话「The network created by
this method will not have Internet access.」—— 但对**镜像**够用（镜像走局域网内直连）。真要用它，
有两处必须先解决：

1. 开了不等于能用：另一端得连上这个热点（电视端可用 `WifiNetworkSpecifier` 请求连接，或用户
   手动连 SSID）。
2. **DLNA 那条路会断网**：本地热点不给客户端上网，而 DLNA 给接收端的是一条 URL，接收端要
   自己去互联网拉流 —— B 站那类会直接放不出画面。所以现实形态是「网线继续上网 + Wi-Fi 连热点」
   的双网卡，而**核心的 mDNS / SSDP 广播必须挑对网卡**（现在按「实际的局域网」挑，双网卡下未必
   是热点那张）。这是整个方案里最难的一处。
