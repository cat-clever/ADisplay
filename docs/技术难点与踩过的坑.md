# 技术难点与踩过的坑

这份文档收集**实现过程中真正卡住过、或差点卡住**的问题，以及最后的解法。它不是规格
（那是 `跨平台投屏接收端软件开发文档v2…md`），也不是进度表（那是 `进度与已知问题.md`）——
它是**「为什么代码写成这样」的索引**：每条都给出当时的现象、根因、以及解法。

写它的理由很实际：这些问题里有一大半只在真机上才暴露，而解决它们的证据散落在代码注释里。
集中一份，下次遇到同类现象能先在这里对一眼，而不是从零查一遍。

---

## 一、协议与媒体管线

### 1.1 自己封 MPEG-TS 时踩的四处硬错（Windows 镜像）

**现象**：iPhone 屏幕镜像推送过来，接收端画面起不来或花屏。

**根因**：自封 TS 时有四处不合规，每一处单独看都像小毛病，合起来让解复用器直接放弃：

- **PSI 的 `section_length` 少算 3 字节**：它统计的是「`section_length` 字段之后」的字节数，
  而那 3 个字节（表标识、两个长度字节自身）不算在内。少算的直接后果是解复用器读越界。
- **CRC32 只写了后 2 字节**：PAT/PMT 尾部的 CRC 是完整 32 位，写半个等于无效表。
- **连续性计数器所有 PID 共用一个**：`continuity_counter` 是**每个 PID 各自**的 4 位计数，
  共用会让解复用器认为丢包。
- **声明了 PCR 却没有包真正携带它**：`PCR_PID` 声明了就必须周期性出现在自适应字段里，
  而且要给得比该帧的 PTS 早（这里取 18000 ticks）。
- 另外 **`PES_packet_length` 必须把 AUD（访问单元分隔符）算进去**，漏了会让某些解码器
  把帧切错。

**解法与验证**：按上面逐条改正；验证手法是**用 Python 复刻一遍字节布局**，再拿
`ffprobe` / `ffmpeg` 当裁判读这份 TS，并与 ffmpeg 自己生成的 TS 逐位对照。
「自己写的规格实现 → 让权威实现来判」这条路比肉眼盯着十六进制靠谱得多。

### 1.2 实时流不能交给会缓冲的播放器（镜像延迟的根因）

**现象**：Windows 镜像有画面有声音，但画面慢一两秒，而且播放一会儿会自己断开。

**根因**：一开始把镜像流交给 Media Foundation 播放，而它是**先攒后播**的：启动要攒
约 12.6 秒，而且每次重新缓冲都会在这个基础上再叠（实测三分钟从 12.6 秒涨到 27.1 秒）。

**解法**：镜像这一路改成**核心自解码**（FFmpeg → BGRA），界面只负责「把最新一帧画出来」——
丢掉中间帧也不补帧，因为实时镜像要的是「最新」而不是「完整」。同时：

- 解码器线程数设 1（多线程解码会引入排队延迟）；
- 日志窗口**合并刷新**（最多每 250 ms 刷一次）——每来一行日志就把 500 行重拼一遍是
  O(n) 的界面线程开销，而投屏时日志每秒几十行，界面线程会被它吃掉相当一块，表现就是
  「画面一卡一卡」。

**这条的普适结论**：DLNA 那种「给一条 URL」的播放交给平台播放器（它做硬解与音画同步很成熟），
但**实时镜像不行** —— 两者的要求不同，所以三端现在走两条不同的路。

### 1.3 AAC-ELD：三端各走各的路

**现象**：镜像有画面没声音。

**根因**：AAC-ELD 在 Windows 的 Media Foundation 与 Android 的 MediaCodec 上都不保证支持。

**解法**：核心里用 FFmpeg 解 AAC-ELD（一份实现三端通用）**除 Android 外**——
Android 的 MediaCodec 本来就认它，把 FFmpeg 静态链进 APK 会让包涨到 128 MB 左右。
所以 `vcpkg.json` 里 ffmpeg 标着 `platform: "!android"`，`core/pipeline` 在 Android 上
把换封装那部分源文件换成替身。

### 1.4 AirPlay 的「能力位」把两个 32 位半字拼反了

**现象**：iPhone 的「屏幕镜像」能连上这台设备，但**不投画面**。

**根因**：能力位（features）被拆成两个 32 位半字传输，约定是**第一个在低位、第二个在高位**，
拼反了手机就认为这台设备不支持镜像。

**教训**：这类「连得上但不干活」的协议问题，根因往往在一个字段的位序上 —— 抓包对比一台
能正常工作的设备是最快的定位方式。

### 1.5 UxPlay 会把自己的镜像会话拆掉

**现象**：投屏一会儿自己断开，日志里能看到对 `/info` 的探测请求。

**根因**：UxPlay 收到 BLE 信标探测时会「接管」连接，而那个检查把正常的镜像会话也算了进去。

**解法**：给 UxPlay 打补丁，把接管条件收紧成「请求里带 cseq **且**是已登记的连接」。
配套做了一件同样重要的事：**在 CMake 配置期显式检查补丁是否真的打上了**，锚点找不到就
`FATAL_ERROR`。理由是 ExternalProject 会把补丁步骤的输出藏起来 —— 上游改了文件导致补丁
静默失效的话，表现是「手机会每隔一阵断一次投屏」，极难查。

### 1.6 「真正断开」AirPlay 会话

**难点**：点了「断开投屏」要让 iPhone 真的停，而不是只把本地画面关掉。

**解法**：走 UxPlay 公开的 `raop_remove_known_connections` —— 它只把连接标记成待删，
**不停 httpd、也不撤 mDNS**，所以服务还在、手机随后还能再投。拆除链是：
`httpd_remove_connection` → `conn_destroy` → `raop_rtp_mirror_destroy` → 镜像线程退出时回调
`mirror_video_running(false)` → 我们的 `on_mirror_stopped` → `close_session`。

因为实际拆除发生在 httpd 线程、是异步的，所以之后**还要**显式 `force_close(session_id)`，
让界面立刻收到 `on_session_closed`（否则横幅要等一会儿才消失）。

**DLNA 无法照做**：DMR 协议里接收端是被动方，命令不了手机停止。只能结束本地会话 + 推一条
`STOPPED` 的 GENA 事件，手机认不认取决于对方的 App —— 所以界面文案不能承诺「手机已停止」。

### 1.7 色彩转换交给 swscale，不要自己写

尝试过手写 YUV → BGRA（当时想省一个依赖），对照 ffmpeg 验证后最大差 1，看起来能用。
但**色度矩阵与量化范围必须按帧里带的 colorimetry 来选**，自己写就要把这些分支全实现一遍。
最后还是用 swscale —— 库里的正确性是被无数场景验证过的，没有必要自己维护一份。

## 二、各平台的坑

### 2.1 Windows：CsWinRT 的接口强转

**现象**：镜像**既没有声音也没有画面**（两个症状同一个根因）。

**根因**：对 WinRT 投影对象做 C# 风格的强转 `(IBufferByteAccess)obj` 会抛
`InvalidCastException` ——投影对象是 RCW 包装，「看起来是」但转不过去。

**解法**：必须用 `obj.As<IBufferByteAccess>()`（`WinRT` 命名空间提供的扩展）。
这个坑一次踩掉两个功能，所以值得单独记一条。

### 2.2 Windows：AudioGraph 的 `RequiredSamples` 是帧数

**现象**：有画面没声音。

**根因**：`FrameInputNodeQuantumStartedEventArgs.RequiredSamples` 给的是**帧数**，
而 `AudioFrame` 的缓冲区大小要按 `帧数 × 声道数 × 4`（32 位浮点）算。按帧数申请就少了大半。

### 2.3 Windows：绿色版没有「包身份」

**现象**：语言偏好这类设置，用 `ApplicationData.Current.LocalSettings` 会直接抛异常。

**根因**：这个 API 需要包身份（MSIX），而本项目是绿色版 zip（csproj 里
`WindowsPackageType=None`）。

**解法**：自己往 `%LOCALAPPDATA%\ADisplay\` 下写文件（启动日志早就是这么做的）。
同样地，Windows 的 `.resw` + `x:Uid` 资源系统也只在解析 XAML 时取一次值，所以界面语言
改成「一份字符串表 + 语言变化时逐个回填」。

### 2.4 Windows：两个窗口的关闭语义

**现象**：点主窗的 X，第一次只关掉日志窗，要再点一次进程才退。

**根因**：两个独立线索都真实发生过 ——
（1）日志窗默认位置**正好压在主窗标题栏上**，第一次点击落在了日志窗的 X 上；
（2）关窗收尾（销毁播放器与引擎）**可能卡住**，而日志窗那一步很快、看得见，
后面几步卡住就完全没有反馈。

**解法**：（a）日志窗摆到主窗标题栏下方，别压住关闭按钮；（b）收尾有上限
（3 秒，超时直接退出，**保证点一下就一定退**）；（c）每一步的耗时写进启动日志 ——
下次再出现，一眼就能分开是「卡住」还是「点在别的窗口上」。

顺带一条与它相关的设计：关闭语义是**单向**的（关日志窗只关它自己；关主窗强制把日志窗一并
收掉）。反过来的双向语义会让用户以为「关掉日志就等于退出」。

### 2.5 Android：Bionic 缺的那些符号

**现象**：交叉编译到最后一步链接失败：`undefined symbol: fwrite_unlocked`；换封装那部分
接上之后又冒出 `glob` / `globfree`。

**根因**：vcpkg 交叉编译出的 `libspdlog.a` 是按它自己的编译期判断编的，用了 glibc 才有的
`fwrite_unlocked`；而 FFmpeg 的 libavformat 探测到 Bionic 头文件里有 glob 声明就用了它，
但那个符号是 API 28 才提供的，本项目按 android-24 构建。

**解法**：**补符号**（`platform/android/src/LibcCompat.cpp`），而不是去 patch 第三方依赖
（下次升级还得再来一次）。两个细节：

- 必须编进**共享库本身**，不能放进某个静态库 —— 静态库成员只在被引用时才拉进来，
  而引用它的 `libspdlog.a` 排在链接行后面，顺序上不保证取得到。
- glob 那份不能写成「永远返回错误」的空壳：本项目正常路径不走到它（远端字节由自己的
  HTTP 客户端取回，从不把本地路径通配交给 avformat），但**一旦被走到就必须是对的**，
  否则等于把链接错误换成了静默的运行时错误。

### 2.6 Android：前台服务类型与开机自启

**现象**：开机自启在 Android 15 上会静默失效。

**根因**：Android 15 起，从 `BOOT_COMPLETED` 接收器起前台服务有一张**禁止名单**：
`dataSync`、`camera`、`mediaPlayback`、`phoneCall`、`mediaProjection`、`microphone`。
硬起会抛 `ForegroundServiceStartNotAllowedException` —— 服务起不来、接收也就没了，
而且只有在真机上才看得到。

**解法**：开机那一路报 `connectedDevice`（不在名单里，且更贴合它当时真在做的事：
守着局域网等手机连进来），界面按开的那一路仍报 `mediaPlayback`。两个类型都要写进清单的
`android:foregroundServiceType`，否则 Android 14+ 会按声明的类型校验。
`connectedDevice` 要求的条件（声明 `CHANGE_WIFI_MULTICAST_STATE` 等之一）本来就满足。

### 2.7 Android：TV 界面上的两个反复出现的错

- **按钮在窄屏上被挤出屏幕**（踩过两次：待机页那三个服务按钮、画质档位那一行）。
  根因是「多个等宽内容挤在一行 + 固定宽度/带标签」。解法：**用 `Modifier.weight(1f)` 等分
  整行宽度**，标签另起一行，按钮上只留短词。
- **`androidx.tv.material3.Button` 在触屏上点击不生效**：那个组件的交互模型建立在
  「焦点 + 方向键」上。而本项目要求同一个 APK 既能跑在电视（只有遥控器）又能跑在
  手机/平板（触屏），所以自己用 `clickable` + `focusable` 拼了一个 `ActionButton`。

### 2.8 macOS：Swift 并发的两个限制

- `NSWindowDelegate` 是 `@MainActor` 隔离的，不能随便挂到非隔离的类型上。
- **C 函数指针回调不能捕获上下文**（音频回调就是这种），所以门禁（挂起/恢复）要放在
  被调用的那个 Swift 类型内部，而不是在回调闭包里捕获 `self`。

## 三、构建与依赖

### 3.1 vcpkg 二进制缓存与 GitHub 缓存的三条规矩

这三条都是被时间咬出来的（一次 tag 轮次从 4 分钟变成 18–21 分钟）：

- **GitHub 的缓存按 ref 分域**：tag 上创建的缓存别的 ref 读不到，只有**默认分支**上创建的
  缓存所有 ref 共享。所以发版是 tag 触发的，只有 main 上跑过的那份缓存能被复用。
- **改了依赖（或新增一个三元组）之后，要先在 main 上跑一轮**再打 tag。否则每个 tag 轮次
  都发现要的东西不在缓存里，于是从头编 FFmpeg（Windows 上十几分钟）。
- **同一平台的多个三元组要合在同一个任务、共用同一次缓存调用**：vcpkg 的二进制缓存是
  整目录恢复/保存的，合成一个任务两套包才躺在同一个条目里；拆成两个任务各存各的键，
  一个任务存的包另一个读不到，等于每轮都要重编。

### 3.2 Android 的两个 ABI

- `abiFilters` 里**每多列一个 ABI 就等于承诺它也有 `.so`**：列了却没有，Android 安装时不报错，
  装上跑起来才在 `System.loadLibrary` 处抛 `UnsatisfiedLinkError`（表现是「装上就闪退」）。
  所以加 ABI 的顺序是「先在 CI 里编出来，再往 `abiFilters` 里加一行」。
- 复用的 vcpkg 三元组要挑 NEON 档位一致的：`arm-neon-android`（NEON 开）而不是社区的
  `arm-android`（NEON 关）—— 依赖与核心库必须同一档，否则基础库里按 NEON 编出来的代码
  会被不带 NEON 的调用方走进去。
- 32 位 ARM 没有原生 64 位原子操作：一度担心要补 `libatomic`，实测 armv7-a 的
  `ldrexd` / `strexd` 由编译器内联展开，不需要。
- x86 / x86_64 有意不做：只有模拟器与极少数 x86 盒子用得上，而每多一个 ABI 都要多编一份
  核心库外加一截 APK 体积。

### 3.3 本机没有 Android SDK 与 Xcode

后果很直接：**Kotlin / Swift / C# 的改动没有任何本地编译机会，CI 是唯一的编译器**。
所以「打 tag → 编挂 → 修 → 删 tag 重打」是这里的常态流程（删 tag 前先确认没有已发布的
Release）。配套的做法是写完先按「开发流程上的坑」那一节自查一遍。

## 四、界面与交互

### 4.1 日志与界面文字是两件事

- **日志一律中文**，不跟着界面语言走：它是给人排查用的，核心里几百条中文长句翻一遍的
  收益远小于成本。
- **界面**做中英双语，且要求**切换不重启应用** —— 这一条直接决定了不能用系统那套
  「启动时按 Configuration 取一次值」的资源系统（Android 的 `values/`、macOS 的
  `Localizable.strings`、WinUI 的 `.resw` + `x:Uid` 都是那个模型）。三端因此各自拿一份
  字符串表 + 一个语言状态：Compose 靠重组、SwiftUI 靠 `@Published`、WinUI 靠一遍
  显式的回填（XAML 的字是解析时定下的）。

### 4.2 够不着的边界

应用名（Android 的 `strings.xml`、macOS / Windows 的窗口标题）是系统在创建时读一次，
跟不了应用内语言；核心给出的少数提示（设备名校验的具体原因）也是中文 —— 要翻得给 C ABI
加错误码或做码表映射。这两条都写进了注释，免得以后被当成 bug 反复查。

### 4.3 输入方式要分开提示

电视端同时可能被遥控器与触屏操作。提示文案要跟着变（「用遥控器选中并按确定」/「点击」），
写反了会让人对着屏幕按半天。同理，只有遥控器设备才自动抢焦点 —— 触屏上抢焦点会留下一个
一直挂在按钮上的焦点框，看起来像没点干净。

## 五、诊断方法（这一节最值得复用）

### 5.1 启动日志：抓「进程活着但没有窗口」

Windows 端的 `StartupLog` 由**模块初始化器**写入，比核心的日志还早，成对记录
「进入/离开」每个启动步骤（构造函数、`InitializeComponent`、创建引擎…）。
日志断在哪个「进入」上就是死在哪一步 —— 它专治「双击没反应、进程却活着」这类最难查的坏法。
写日志的路径有两处候选（exe 同目录优先）且写不了就静默放弃：写不了日志不该让程序多一个死法。

### 5.2 先量，再改

镜像延迟那次不是靠猜：先在诊断里打印「从核心交下一帧到画上屏花了多少毫秒」，确认瓶颈在
上游还是自己这层，再决定改哪里。类似的判决性诊断还有：伴音的峰值 / 丢帧 / 已送出帧计数，
以及落一份 WAV 到磁盘 —— 用来分开「根本没收到」「收到了没播」「播了没声音」三种情况。

### 5.3 用权威实现当裁判

自封 TS 用 `ffprobe` / `ffmpeg` 判；色彩转换与手写实现对照 ffmpeg 的输出（最大差 1 才算
等价）。凡是「自己实现了某种规格」的地方，都尽量找一个成熟实现来对照，而不是自己盯着
十六进制找感觉。

### 5.4 让日志可读也是一种性能手段

日志窗口合并成最多每 250 ms 刷新一次：既把界面线程的开销降了两个数量级，也让投屏时
日志真的看得清（否则每秒几十行滚动，人眼抓不住关键那行）。

## 六、开发流程上的坑

这些不是代码问题，但同样会让一轮 CI 白跑（约 5 分钟），所以一并记下来：

- **编译错误要取全**。只 `grep` 第一条会漏掉后面的：曾经因为只看第一条，把一个
  「C 函数指针回调不能捕获 self」的错误当成编译器的注释而错过。
- **加成员之前先在同一文件里 grep 名字**。`EngineModel` 那个类很大（属性、枚举、
  Compose 状态都在一起），撞名是这里的头号坑。同一天在 `qualityPreset` 与 `language`
  上各踩一次：Kotlin 的 `var foo`（尤其 `by mutableStateOf`）会在 JVM 上生成 `setFoo`，
  所以切换函数不能叫 `setFoo` —— 本仓库的约定是 `applyXxx`。
- **Kotlin 的续行不能以运算符开头**（`+ "…"` 单独起一行会报 `Expecting member declaration`），
  运算符要留在上一行行尾。Swift / C# 允许行首运算符，所以三端同时写同样的多行字符串时，
  只有 Android 会挂。
- **C# 的几处可见性/命名**：public 类的方法与构造不能收 internal 的参数类型（`CS0051`），
  通常该降成员可见性而不是把类型提成 public（提了往往引出下一处）；方法名不能与类型名
  同名（`LanguageStore.Strings()` 会让类里的 `Strings.Of(...)` 解析成方法自己）；
  把方法从 static 改成实例时**签名那一行也要改**（只改方法体会报 `CS0120`）。
- **临时文件放 `apk/`**（仓库的忽略目录）。放在项目根目录的调试脚本会被 `git add -A`
  扫进版本库 —— 已经发生过两次。
- **界面里出现了不该有的说法时，先怀疑文档**：曾经把「全 ABI」写进 README 当成已完成
  （其实只打了一个 ABI），也曾经让安装说明教用户去选一个**根本不存在的**画质档位。
  状态类文档要照着代码核，不能照着需求文档抄。
