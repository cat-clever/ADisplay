# 跨平台投屏接收端（PC）软件开发文档

版本：v1.2　｜　日期：2026-10-08　｜　支持：iOS（AirPlay）、Android（DLNA / 自研协议 / Miracast 可选）；接收端：Windows、macOS、电视（Android TV）；用途：仅个人自用

## 1. 项目概述

### 1.1 目标

开发一款运行在 Windows、macOS（后续扩展 Linux）以及电视 / 电视盒子（Android TV / Google TV）上的**投屏接收端**软件。手机与电脑处于同一局域网时，无需连线，手机即可发现电脑并将屏幕画面、声音、视频投射到电脑上显示。

**使用范围：仅个人自用，不对外发布。** 因此：

- 不上架应用商店，不需要正式签名、公证、审核和自动更新，电视端用 APK 侧载即可。
- 法律与许可证风险大幅降低（见 3.1.3 和第 11 节），但 AirPlay 兼容性仍会随 iOS 升级变化，需要自己跟进维护。
- 体验类功能可按需裁剪：白名单、多设备排队、录屏等可以后置或省略；设备名称修改保留。

### 1.2 支持范围

| 手机系统 | 投屏方式 | 对应协议 | 优先级 |
| --- | --- | --- | --- |
| iOS / iPadOS | 控制中心「屏幕镜像」 | AirPlay 镜像（含 AirPlay 音频） | P0 |
| iOS / iPadOS | 视频 App 内投屏按钮 | AirPlay 视频（HLS 推送） | P1 |
| Android | 视频/音乐 App 内「投屏」按钮 | DLNA / UPnP（媒体推送） | P0 |
| Android | 整屏镜像 | 自研协议（配套 Android 客户端） | P1 |
| Android | 系统自带「多屏互动 / Smart View」 | Miracast（依赖 Wi-Fi Direct） | P2（可选） |

> 说明：Google Cast 接收端需要 Google 授权，无法自由实现，本项目不纳入范围。

### 1.3 接收端运行平台

| 平台 | 形态 | 实现方式 | 优先级 |
| --- | --- | --- | --- |
| Windows 10 / 11（x64、ARM64） | 桌面软件 | C++ 核心 + Qt 6 界面 | P0 |
| macOS 12+（Apple Silicon M 系列 + Intel，Universal 通用包） | 桌面软件（菜单栏常驻） | 同一套 C++ 核心 + Qt 6 界面，VideoToolbox 硬解 | P0 |
| Android TV / Google TV / 安卓电视盒子（ARM 与 x86） | 电视 App（APK） | Kotlin 界面 + NDK 调用 C++ 核心 | P0 |
| Linux（Ubuntu / 统信 UOS 等） | 桌面软件 | 同 Windows / macOS，VAAPI 硬解 | P2 |
| 鸿蒙智慧屏、各品牌定制电视系统 | 电视 App | 视系统开放程度与应用市场政策评估 | P2 |

> 说明：Apple TV（tvOS）以及较新型号的三星、LG、索尼等品牌电视，多数已自带 AirPlay 接收能力，无需重复开发；三星 Tizen、LG webOS 属于封闭的 Web 应用环境，难以直接实现底层协议服务，暂不纳入首发。

### 1.4 术语

- **Sender / 发送端**：手机。
- **Receiver / Sink / 接收端**：本软件（运行在电脑上）。
- **mDNS / Bonjour**：局域网服务发现（UDP 5353）。
- **SSDP**：UPnP 设备发现（UDP 1900，组播 239.255.255.250）。

## 2. 需求说明

### 2.1 功能需求

1. **设备发现**：软件启动后自动在局域网广播，手机的投屏列表中出现设备名称（可随时修改，例如「客厅电脑」，详见 2.4）。
2. **屏幕镜像**：接收并实时显示手机画面，支持横竖屏切换自动旋转。
3. **音频播放**：镜像同时播放手机系统声音，音画同步。
4. **媒体推送**：接收手机 App 推送的视频/音乐 URL，由电脑端播放，并支持手机端暂停、快进、调音量。
5. **连接管理**：首次连接可弹窗确认或输入 PIN 码；支持白名单、黑名单、同时连接数限制。
6. **窗口功能**：窗口/全屏切换、置顶、画面缩放、截图、录屏（P2）。
7. **托盘常驻**：开机自启、最小化到托盘、一键开关接收服务。
8. **多语言**：简体中文、English。

### 2.2 非功能需求

| 指标 | 目标 |
| --- | --- |
| 镜像端到端延迟 | ≤ 200 ms（局域网 5GHz Wi-Fi，1080p30） |
| 分辨率/帧率 | 最高 1080p@60fps，逐步支持 4K |
| CPU 占用 | 硬件解码时 ≤ 15%（主流 i5 级别） |
| 稳定性 | 连续镜像 4 小时无崩溃、无内存增长 |
| 启动时间 | 冷启动 ≤ 3 秒 |
| 兼容性 | 接收端 Windows 10 1909+/Windows 11、macOS 12+、Android TV 8+；手机端 iOS 14+、Android 8+；CPU 架构要求见 2.5 |

### 2.3 macOS 与电视端专项需求

**macOS**

- 菜单栏常驻图标，支持开机自启、窗口 / 全屏切换，提供 Apple Silicon 与 Intel 通用（Universal）安装包。
- 首次启动引导用户授予「本地网络」权限，并检测系统自带「AirPlay 接收器」是否占用 7000 端口（见 4.5）。
- 自用无需付费开发者账号与公证：本机编译运行，拷到自己的其他 Mac 时用 ad-hoc 签名，并在「隐私与安全性」中放行。

**电视端**

- 10 英尺界面：大字号，遥控器方向键与「确定 / 返回」键即可完成全部操作，不依赖触屏或键鼠。
- 连接确认与 PIN 码直接显示在电视屏幕上，用遥控器选择「允许 / 拒绝」。
- 开机自启并以前台服务常驻，待机时低功耗；投屏开始时自动全屏并置于最上层，结束后回到待机页。
- 待机页显示设备名称、局域网 IP 和连接说明（含二维码），方便手机用户找到设备。
- 低端电视盒子（1–2 GB 内存）以 1080p30 流畅为目标，设置中提供「流畅 / 均衡 / 高清」画质档位。
- 支持有线网络；推荐 5GHz Wi-Fi 或网线，以降低延迟与丢包。

### 2.4 设备名称可修改

所有平台（Windows、macOS、电视端）都支持用户自定义设备名称，手机投屏列表里显示的就是这个名称。

- **默认名称**：桌面端取电脑主机名，电视端取设备型号，首次启动即可修改。
- **修改入口**：桌面端在「设置 → 设备名称」，托盘 / 菜单栏菜单中也提供快捷修改；电视端在设置页通过遥控器和屏幕键盘输入，并提供「客厅」「卧室」等常用预设。
- **输入规则**：1–32 个字符，支持中文、字母、数字、空格和常见符号；不能为空，自动过滤控制字符。
- **即时生效**：保存后 DiscoveryService 注销并重新注册 mDNS（AirPlay、自研协议）以及 SSDP/UPnP 的显示名称（DLNA），无需重启软件。手机端列表可能有几秒的刷新延迟。
- **标识不变**：只更改显示名称，设备唯一标识（deviceid / UUID）和已配对记录保持不变，已连接过的手机不需要重新配对。
- **重名处理**：局域网内出现同名设备时，自动追加数字后缀（如「客厅电脑 (2)」）。
- **持久化**：名称保存在本地配置文件中，软件升级后保留。

### 2.5 CPU 架构支持（ARM 与 x86）

三个接收端都要同时支持 ARM 与 x86 两类 CPU，苹果端要同时覆盖 M 系列（Apple Silicon）与 Intel 芯片。

| 平台 | 需覆盖的架构 | 构建与注意事项 |
| --- | --- | --- |
| Windows | x64、ARM64（如骁龙 X 系列的 Windows 笔记本） | 第三方库用 vcpkg 的 x64-windows 与 arm64-windows 两套三元组分别编译；Qt 6 选用对应架构的 MSVC 版本；ARM64 上原生运行，不依赖 x64 转译；硬解统一走 D3D11VA，NVDEC / QSV 仅适用于对应的 x64 显卡 |
| macOS | Apple Silicon（M1 / M2 / M3 / M4 等 M 系列）、Intel | 以 CMAKE\_OSX\_ARCHITECTURES="arm64;x86\_64" 构建 Universal 通用二进制；第三方库分别编译两种架构后用 lipo 合并；VideoToolbox 与 Metal 在两种芯片上都可用，不依赖 Rosetta 2 |
| Android TV | arm64-v8a、armeabi-v7a、x86\_64、x86 | 用 NDK 为每个 ABI 分别编译 C++ 核心及 FFmpeg、OpenSSL 等依赖；自用时一个 APK 打包全部 ABI 即可，不必在意体积；新版 NDK 默认满足 16 KB 页大小对齐，较新设备需要 |

补充说明：

- 32 位 x86 的 Windows 不在范围内，如有需要再单独评估。
- 代码层面不做架构假设：使用定长整数类型，显式按字节序读写协议包头，不直接把缓冲区强转为结构体；不写内联汇编。
- 性能优化按架构选择：FFmpeg 编译时启用对应的 SIMD（x86 的 SSE/AVX、ARM 的 NEON）；OpenSSL 会自动使用 AES-NI 或 ARMv8 加密指令。
- 构建体系统一用 CMake 工具链文件区分架构，脚本一键产出各架构的包。
- 测试至少各备一台真机：Windows ARM64、Apple Silicon Mac、Intel Mac、ARM 电视盒子；x86 电视设备若没有，可用 x86 模拟器验证功能，但不能代表真实性能。

## 3. 协议技术方案

### 3.1 AirPlay（iOS 投屏，P0 重点）

#### 3.1.1 协议概览

AirPlay 由多套子协议组成，接收端需同时实现：

| 组件 | 作用 | 传输 |
| --- | --- | --- |
| Bonjour 服务广播 | 让 iPhone 发现设备（`_airplay._tcp`、`_raop._tcp`） | mDNS / UDP 5353 |
| HTTP / RTSP 控制通道 | 获取设备信息、配对、建立会话 | TCP（常用 7000） |
| 配对与认证 | 设备配对、会话密钥协商 | HTTP 接口 `/pair-setup`、`/pair-verify`，FairPlay 握手 `/fp-setup` |
| 镜像视频流 | H.264 视频，加密传输 | TCP 数据端口 |
| 音频流（RAOP） | ALAC / AAC-ELD，RTP 封装并加密 | UDP（数据/控制/时间三个端口） |
| 时间同步 | NTP 风格时间戳，实现音画同步 | UDP timing 端口 |
| 视频推送（AirPlay Video） | iPhone 仅发送 HLS 地址，由接收端自行拉取播放 | HTTP |

#### 3.1.2 连接流程

1. **广播**：接收端注册 mDNS 服务，TXT 记录包含 `deviceid`（MAC 风格唯一 ID）、`features`（能力位）、`model`、`srcvers`、`pk`（公钥）等。`features` 决定 iPhone 是否显示「屏幕镜像」入口。
2. **查询信息**：iPhone 对接收端发起 `GET /info`，接收端以二进制 plist 返回设备能力。
3. **配对 / 认证**：执行 `pair-setup` → `pair-verify`（基于 Ed25519 / Curve25519 的密钥交换），再进行 FairPlay 的 `fp-setup` 两轮握手，得到用于解密流的会话密钥材料。
4. **SETUP**：第一次 SETUP 传递加密密钥、IV、时间同步方式；第二次 SETUP 声明流类型（镜像视频、音频），接收端返回各流的数据/控制/时间端口。
5. **RECORD → 传输数据**：
   - 镜像视频：TCP 连接上每个包带固定长度包头（含载荷长度、载荷类型、时间戳）；类型区分「编码参数（SPS/PPS）」「视频码流」「心跳」。载荷使用 AES-CTR 加密，需用握手得到的密钥解密。
   - 解密后的数据为 AVCC 格式 H.264，需转换为 Annex B 再送入解码器。
   - 音频：RTP 包，AES-CBC 加密，解密后送入 ALAC 或 AAC-ELD 解码器。
6. **维持与断开**：周期性心跳，`FLUSH` 清缓冲，`TEARDOWN` 结束会话。

> 注意：以上字段细节（包头布局、密钥派生方式等）请以开源实现源码为准逐项对照验证，不要仅凭本文档实现。

#### 3.1.3 实现路线与法律风险

- **参考开源项目**：UxPlay、RPiPlay、shairplay（均为逆向实现的 AirPlay 接收端），可作为协议细节与行为的对照参考，请注意各自的开源许可证（多为 GPL 系列），仅自用且不分发时可以直接复用其代码（GPL 的开源义务主要在分发时产生），将来若对外分发则需按许可证开源。
- **FairPlay 风险**：AirPlay 镜像依赖 Apple 的 FairPlay 认证机制，市面第三方实现均为逆向工程，存在版权/合规与兼容性风险（iOS 大版本升级可能导致失效）。本软件仅个人自用、不对外分发，法律风险较低，建议只在自己的设备和网络内使用；协议适配层仍建议保留，便于 iOS 升级后快速修复。
- **替代思路（降低风险）**：提供配套 iOS App 走自研协议——但 iOS 整屏录制需使用 ReplayKit 广播扩展，有内存限制（约 50MB）与上架审核成本，体验不如系统原生 AirPlay，建议仅作备选。

### 3.2 DLNA / UPnP（Android 媒体推送，P0）

适用于 Android 上绝大多数视频 App（B 站、爱奇艺、腾讯视频等）的「投屏」按钮。

- **设备角色**：DMR（Digital Media Renderer，数字媒体渲染器）。
- **发现**：SSDP 组播应答 `M-SEARCH`，并周期性发送 `NOTIFY alive`；通过 HTTP 提供设备描述 XML。
- **必须实现的服务**：
  - `AVTransport`：`SetAVTransportURI`、`Play`、`Pause`、`Stop`、`Seek`、`GetPositionInfo`、`GetTransportInfo`
  - `RenderingControl`：`SetVolume`、`GetVolume`、`SetMute`
  - `ConnectionManager`：`GetProtocolInfo`
- **事件订阅**：支持 `SUBSCRIBE` 向手机回推播放状态（LastChange）。
- **播放**：收到媒体 URL 后交给播放器内核（libmpv 或 FFmpeg）播放，支持 MP4、MKV、HLS(m3u8)、MP3、FLAC 等。
- **参考库**：Platinum UPnP、libupnp（pupnp）、cpp-httplib（自写 SOAP 处理也可行）。

### 3.3 Android 整屏镜像（自研协议 + 配套客户端，P1）

Android 没有无需授权、通用于局域网的系统级镜像协议（Miracast 依赖 Wi-Fi Direct，见 3.4），因此建议提供**配套 Android App**：

**发送端（Android App）**

- `MediaProjection` 获取屏幕 → `MediaCodec` 硬编码 H.264（可配置 1080p / 30–60fps / 4–12Mbps，低延迟模式、关闭 B 帧）。
- `AudioPlaybackCapture`（Android 10+）采集系统声音，AAC/Opus 编码。
- 前台服务保持运行，通知栏提供停止按钮。

**传输协议（二选一）**

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| WebRTC | 自带 NAT 穿透、拥塞控制、抗丢包，延迟低 | 集成体积大，调试复杂 |
| 自定义 TCP/UDP（H.264 NAL + 简单包头） | 实现简单，可控，延迟极低 | 需自行处理丢包、重传、关键帧请求 |

建议：MVP 先用「自定义 TCP + 关键帧请求」，稳定后评估迁移 WebRTC。

**发现与配对**

- 电脑端广播 `_castpc._tcp`（自定义服务名）；手机 App 通过 NsdManager 发现。
- 备选：二维码扫码（二维码含 IP、端口、一次性令牌），可避开部分路由器屏蔽组播的问题。
- 首次连接用 6 位 PIN 确认，之后以设备证书/令牌免确认。

### 3.4 Miracast（可选，P2）

- Miracast 基于 Wi-Fi Direct（P2P）而非普通局域网，手机与电脑不必在同一路由器下，但需要网卡支持。
- Windows 10/11 已内置接收功能（设置 →「投影到此电脑」，需安装「无线显示器」可选功能）。**建议直接引导用户启用系统自带功能**，自研 Miracast Sink 的成本与兼容性代价极高。
- 可在软件设置页提供「检测并一键打开系统投影设置」入口。

## 4. 系统架构

### 4.1 总体分层

```
┌──────────────────────────────────────────────┐
│ UI 层：主窗口 / 投屏窗口 / 托盘 / 设置            │
├──────────────────────────────────────────────┤
│ 会话管理层：连接确认、PIN、白名单、多会话调度       │
├───────────────┬───────────────┬──────────────┤
│ AirPlay 模块    │ DLNA 模块       │ 自研协议模块     │
│ (mDNS+RTSP+    │ (SSDP+SOAP)    │ (mDNS+TCP)   │
│  配对+镜像+RAOP)│                │              │
├───────────────┴───────────────┴──────────────┤
│ 媒体管线：解密 → 解复用 → 解码（硬件优先）→ 同步    │
├──────────────────────────────────────────────┤
│ 渲染/音频输出：D3D11 / OpenGL 渲染，WASAPI 音频   │
├──────────────────────────────────────────────┤
│ 基础设施：网络、日志、配置、加密、线程池、更新       │
└──────────────────────────────────────────────┘
```

### 4.2 核心模块职责

| 模块 | 职责 |
| --- | --- |
| DiscoveryService | 统一管理 mDNS 注册与 SSDP 应答，网卡变化（切换 Wi-Fi、插拔网线）时自动重新注册 |
| AirPlayServer | HTTP/RTSP 服务、配对与 FairPlay 握手、镜像流/音频流接收、时间同步 |
| DlnaRenderer | UPnP 设备描述、SOAP 动作、事件订阅、调用播放内核 |
| CastProtocolServer | 自研协议的握手、PIN 校验、码流接收、关键帧请求 |
| SessionManager | 会话生命周期、权限校验、多设备排队/抢占策略 |
| MediaPipeline | 抖动缓冲（Jitter Buffer）、音画同步、解码器封装 |
| Renderer | 视频渲染、旋转/缩放/全屏、截图 |
| AudioOutput | 重采样、音量、WASAPI 低延迟输出 |
| Settings | 设备名称、画质、自启、端口、日志级别 |

### 4.3 关键接口（示意）

```cpp
// 所有协议模块实现统一接口，便于扩展
class IReceiverProtocol {
public:
    virtual ~IReceiverProtocol() = default;
    virtual bool start(const ReceiverConfig& cfg) = 0;
    virtual void stop() = 0;
    virtual void setListener(IReceiverListener* l) = 0;
};

class IReceiverListener {
public:
    virtual void onConnectRequest(const PeerInfo& peer, ConfirmCallback cb) = 0;
    virtual void onVideoPacket(SessionId id, const VideoPacket& pkt) = 0;  // 已解密的 H.264
    virtual void onAudioPacket(SessionId id, const AudioPacket& pkt) = 0;
    virtual void onMediaUrl(SessionId id, const std::string& url) = 0;    // DLNA / AirPlay Video
    virtual void onSessionClosed(SessionId id, CloseReason reason) = 0;
};
```

### 4.4 线程模型

- 网络 IO 线程（每协议一个事件循环）
- 解密/解复用线程
- 解码线程（硬件解码优先，失败自动降级软解）
- 渲染线程（与 UI 线程分离，使用 VSync 或最新帧策略）
- 音频线程（高优先级，低延迟 WASAPI 共享/独占模式）
- 低延迟原则：**视频只保留最新帧，积压则丢帧**，不做长缓冲；音频缓冲 ≤ 50–100 ms。

### 4.5 多平台适配

核心思路：协议、会话、解密、解复用和音画同步逻辑全部放进**一套跨平台 C++ 核心库**（castcore），各平台只实现渲染、音频输出、硬件解码、界面和分发这几层薄适配，避免同一协议维护三份代码。

| 项目 | Windows | macOS | Android TV |
| --- | --- | --- | --- |
| 服务发现（mDNS） | 系统 DNS-SD API 或 Bonjour | 系统自带 Bonjour（dns\_sd.h） | NsdManager 或 JmDNS，并持有 MulticastLock |
| 视频硬解 | D3D11VA / NVDEC / QSV | VideoToolbox | MediaCodec（Surface 直出） |
| 视频渲染 | Direct3D 11 | Metal | SurfaceView |
| 音频输出 | WASAPI | CoreAudio | AudioTrack（低延迟）或 Oboe |
| 界面 | Qt 6 | Qt 6（菜单栏常驻） | Kotlin + Compose for TV（遥控器焦点导航） |
| 自启与常驻 | 计划任务 + 托盘 | 登录项 + 菜单栏 | BOOT\_COMPLETED + 前台服务 |
| 打包分发 | 绿色版 exe 或简易安装包 | 本机编译 + ad-hoc 签名（无需公证） | APK 侧载（adb 或 U 盘安装） |

平台特有注意事项：

- **macOS 端口冲突**：macOS 12 及以上系统自带「AirPlay 接收器」，会占用 5000 与 7000 端口并广播自己的 AirPlay 服务。启动时检测端口，被占用则提示用户在系统设置中关闭「AirPlay 接收器」，或改用其他端口。具体行为请在目标系统版本上实测确认。
- **macOS 权限**：较新的 macOS 版本访问本地网络需要用户授权，Info.plist 中需声明 NSLocalNetworkUsageDescription 与 NSBonjourServices。
- **电视端清单**：声明 leanback 启动入口，触屏设为非必需（`android.hardware.touchscreen` 的 required=false），提供 320×180 横幅图标；mDNS 需要 CHANGE\_WIFI\_MULTICAST\_STATE 权限。
- **电视端兼容**：优先 MediaCodec 硬解；同时打包 arm64-v8a 与 armeabi-v7a；部分定制电视系统会清理后台，需引导用户把应用加入自启与省电白名单。

## 6. 网络与安全

### 6.1 端口清单（可配置）

| 用途 | 协议 | 端口 |
| --- | --- | --- |
| mDNS | UDP | 5353（组播 224.0.0.251） |
| SSDP | UDP | 1900（组播 239.255.255.250） |
| AirPlay 控制（HTTP/RTSP） | TCP | 7000（常用） |
| AirPlay 镜像数据 | TCP | 动态（SETUP 返回） |
| AirPlay 音频/控制/时间 | UDP | 动态（SETUP 返回） |
| DLNA 设备描述/SOAP | TCP | 动态或固定（如 49152） |
| 自研协议 | TCP/UDP | 例如 TCP 8765 |

安装程序需添加 Windows 防火墙入站规则，否则手机常常「搜不到设备」。

### 6.2 安全策略

- 首次连接弹窗确认或 PIN 码，防止同网段陌生人投屏骚扰。
- 设备白名单/黑名单；会议室模式下可「仅允许 PIN」。
- 自研协议使用 TLS 或基于预共享密钥的会话加密。
- 不记录屏幕内容；日志中不写入任何画面或敏感数据。
- 接收端仅在用户开启时监听端口，并支持一键关闭。
- 所有输入（plist、SOAP、RTSP 头）做长度与格式校验，防止缓冲区溢出。

### 6.3 常见网络问题与对策

| 问题 | 原因 | 对策 |
| --- | --- | --- |
| 手机搜不到电脑 | 路由器开启 AP 隔离 / 组播被过滤；防火墙拦截 | 检测并提示；提供二维码/IP 手动连接 |
| 多网卡导致广播错误 | 虚拟网卡（VMware、WSL、VPN） | 允许选择广播网卡；默认忽略虚拟网卡 |
| 画面卡顿花屏 | 2.4GHz 拥塞、丢包 | 建议 5GHz；丢包后请求关键帧；降码率 |
| 切换网络后失效 | IP 变化 | 监听网络变化事件，重新注册服务 |

## 7. UI 与交互设计

1. **主窗口**：显示设备名称、本机 IP、服务状态开关、已连接设备列表、二维码（供 Android 客户端扫码）。
2. **投屏窗口**：无边框、可拖拽缩放；手机旋转时自动适配比例；双击全屏；悬浮工具栏（全屏、置顶、截图、断开）。
3. **连接确认弹窗**：显示设备名与类型，选项「允许一次 / 始终允许 / 拒绝」。
4. **设置页**：设备名称、画质预设（流畅 / 均衡 / 高清）、开机自启、端口、白名单、日志导出、检查更新。
5. **托盘菜单**：开启/关闭接收、打开主窗口、退出。

castpc/

├─ platform/

│  ├─ macos/             # Metal、CoreAudio、菜单栏、签名与公证

## 10. 测试方案

- **设备矩阵**：iPhone（iOS 15 / 16 / 17 / 18 及以上）、iPad；主流 Android 品牌（小米、华为、OPPO、vivo、三星）；不同版本的视频 App；接收端覆盖 Windows 10/11、macOS（Intel 与 Apple Silicon）以及主流电视盒子 / 安卓电视（含 1–2 GB 内存的低端机型）。
- **网络场景**：5GHz / 2.4GHz、有线接入电脑、弱信号、丢包 5%、切换 Wi-Fi。
- **性能**：端到端延迟（手机端显示毫秒计时器 + 高速相机或屏幕同拍测量）、CPU/GPU/内存曲线、4 小时长稳。
- **回归**：保存抓包文件做协议回放测试，iOS 升级后优先回归 AirPlay。
- **自动化**：核心解析逻辑（plist、RTSP、SOAP、包头）编写单元测试和模糊测试。

## 11. 风险与应对

| 风险 | 等级 | 应对 |
| --- | --- | --- |
| FairPlay/AirPlay 法律与版权风险 | 低（仅自用） | 只在自己的设备与网络内使用，不对外分发；保持协议层隔离 |
| iOS 升级导致 AirPlay 不兼容 | 高 | 保留抓包回放；关注新版 iOS 变化；自己重新编译修复 |
| 路由器屏蔽组播 | 中 | 二维码/手动 IP；故障诊断工具 |
| 硬件解码兼容性 | 中 | 多解码器后端 + 自动回退软解 |
| 音画不同步 | 中 | 使用协议时间戳 + 主时钟，音频为基准 |
| 开源代码许可证 | 低（仅自用） | 不分发则无开源义务；将来若对外分发需重新评估 |
| macOS 自带 AirPlay 接收器占用端口 | 中 | 启动检测并引导关闭；支持自定义端口 |
| macOS 签名与本地网络权限 | 低 | 自用无需公证；保留首次启动权限引导页 |
| 电视盒子性能弱、定制系统清理后台 | 中 | 硬解优先、画质分档；引导加入自启与省电白名单；真机测试 |
| 多架构依赖库编译与测试成本 | 中 | 统一 CMake 工具链 + vcpkg 三元组；脚本化构建；每种架构至少一台真机 |
